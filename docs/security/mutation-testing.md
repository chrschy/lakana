# Mutation testing: authorization and policy

The M3 epic's exit criterion is "mutation testing on `authz/` and `policy/`." Coverage alone
can't prove a permission check actually denies — a test suite can execute every line of
`GrantAuthorization.authorize` and still never assert that a wrong principal, action, or
securable is refused. Mutation testing closes that gap: [mutmut](https://mutmut.readthedocs.io/)
(`3.8.0`, BSD-3-Clause — confirmed via `scripts/check_licenses.py`) rewrites the target code
one small change at a time (a comparison flipped, an argument replaced with `None`, a
message dropped) and reruns `lakana-core`'s unit tests against each mutant. A mutant that
still passes every test — a *survivor* — is a change in behavior the test suite cannot see.

## Targets

- `packages/lakana-core/src/lakana_core/grants/authorization.py` — `GrantAuthorization`, the
  real grant-resolution algorithm `authorize()`/`permits()` implement.
- `packages/lakana-core/src/lakana_core/policy/` — the row-filter/column-mask expression
  validator, the policy resolver, and the two CRUD services.
- `packages/lakana-core/src/lakana_core/audit/authorization.py` — `AuditingAuthorization`, the
  wrapper that records `AUTHORIZATION_DENIED` audit events.
- `packages/lakana-core/src/lakana_core/catalog/external_location.py` — the `EXTERNAL`-table
  `location_pattern` parser, `claims_overlap`, and `check_claim_free`.

The runner is `lakana-core`'s existing unit test suite (`pytest -m 'not integration'`) — no
separate mutation-specific tests. A mutant is killed exactly when some existing (or,
usually, newly added) unit test fails against it.

## Running locally

```bash
cd packages/lakana-core
uv run mutmut run --max-children 16   # match this to your machine's core count
uv run mutmut results
uv run mutmut show <key>              # inspect one survivor's diff
uv run mutmut run <key>               # re-run just that one mutant after a fix
```

Check that every non-killed mutant is either fixed or recorded as equivalent below, and
that every target still has mutants at all:

```bash
uv run mutmut results --all true | uv run python ../../scripts/check_mutants.py ../../docs/security/mutation-testing.md
```

`scripts/check_mutants.py` parses `mutmut results`' `<key>: <status>` lines. It treats
every status other than `killed`/`skipped` as needing a record and exits `1` — listing the
missing keys — if any survivor's key isn't a table row below. It also fails closed if any
of the four targets (`lakana_core.grants.authorization`, `lakana_core.policy`,
`lakana_core.audit.authorization`, `lakana_core.catalog.external_location`) has *no* mutant
keys at all in the input — a missing `.meta` file, a crashed `mutmut run`, or an
`only_mutate` glob that stopped matching after a rename would otherwise report nothing
wrong and pass vacuously. That check needs `--all true` (not plain `mutmut results`, which
lists survivors only): a target mutmut ran and fully killed must still show up as covered,
which only a killed-inclusive listing can tell apart from a target mutmut never touched.

`mutants/` (mutmut's working copy of the source tree) is git-ignored and never committed.
It also collides with pytest's normal collection if left in place (`import file mismatch`,
since `mutants/tests/*.py` and `tests/*.py` share basenames) — remove it (`rm -rf mutants`)
before running the ordinary test suite again.

## Policy

Every mutant `mutmut results` reports as anything other than `killed` or `skipped` must be
either:

- **killed**, by adding or strengthening a unit test until `mutmut run <key>` reports
  `killed` — the default, and the expected outcome for the overwhelming majority of
  survivors; or
- **recorded as equivalent** below, with the mutant's key, the mutation, and a one-sentence
  reason no input can ever distinguish the mutant's behavior from the original. A cosmetic
  string mutation of an error *message* is not equivalent if some test pins that message —
  pinning the message is preferred over recording it. This applies even when the mutated
  value doesn't change *which branch runs* — `expressions.validate_restricted_expression`
  interpolates its `kind` parameter directly into the error message
  (`f"... is not a valid {kind} expression: ..."`), so a mutation to `kind` is killable by
  pinning that message even though `kind`'s only *behavioral* effect is the `kind == "mask"`
  comparison a non-`"mask"` mutant leaves unchanged.

`scripts/check_mutants.py` is the gate that enforces this in CI (`.github/workflows/mutation.yml`,
weekly). Mutant *keys* are generated by mutmut in the order it walks the AST, so a code
change to a target file renumbers them — the workflow's next scheduled run may then report
new, unrecorded keys even with no behavior change. That's by design: it forces a
re-triage of the actual current mutants rather than trusting stale key numbers, and is why
this is a scheduled job rather than a per-PR gate (it's too slow for that regardless).

SQLAlchemy's `.order_by(None)` cancels ordering, so rows are scanned in whatever order the backend returns them. `check_claim_free`'s own raise/no-raise contract does not depend on scan order: its loop's `continue` statements only skip to the next row, never exiting early, so every candidate row is examined and "some row conflicts" is evaluated the same way regardless of order.
